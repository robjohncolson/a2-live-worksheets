## Confirmed findings (32)

### 1. [high] (student-ux) Recall mode shows the answer on screen the whole time, so the SRS never tests recall

Track 2's whole value is the guided->recall promotion: SM-2 intervals are computed from recall errors/hints. But in recall mode the step narration — which explicitly names the key, e.g. 'Press [STAT] to open the statistics menu' — is rendered unconditionally in BOTH the left walkthrough panel and the calculator narration bar. The mock-LCD footer additionally prints 'Expect [key]'. And every wrong press replies 'Blocked. The next key is [X]' (1 error), which is strictly cheaper than the Hint button (1 hint + 1 error, 2 hints = quality 0). A student in 'recall' just reads the instruction and presses the named key, earning quality 5 forever; the trainer's spaced-repetition data (and the new gradebook score = quality/5) measures nothing. This is the single biggest pedagogy defect for the Sept cohort.

**Where:** ti84-trainer-v2/app.js:2754 (copy = step?.narration, no mode gate), app.js:3111 + 3166 (narration bar), app.js:3415 ('Expect ' footer), app.js:1936 (wrong-key reveals next key), app.js:2444-2445 (hint costs more than a wrong press); narration text: ti84-procedures-data.json one-var-stats step 1

**Suggested fix:** In recall mode, replace narration with a neutral prompt ('Step 3 of 7 — what comes next?') in both the panel and the narration bar, suppress the 'Expect [key]' footer, and make wrongFeedback in recall mode say only 'Not that key' (the commonErrors coaching can stay — it explains why, not what). Reveal the key only via the Hint button so the hint/error economy works.

### 2. [high] (student-ux) Physical-calculator mode (the DEFAULT) is pure honor-system but records perfect scores to the gradebook

physicalMode defaults to true for every new student. In physical mode the step card always shows 'Press [key]' (even in recall mode), and 'I did it' (physicalAdvance) just advances — errors and hints are never counted. So recallQuality(0,0)=5 every time, SM-2 intervals balloon, and recordTrainerAttempt writes score = 5/5 = 1.0 to the roster ledger (source 'trainer') for clicking a button N times without touching any calculator. Guided completions similarly record a fixed 0.8 (lastQuality hardcoded to 4) regardless of performance. The day-old recording feature therefore produces data the teacher can't trust, and students discover the cheapest path is to spam 'I did it'.

**Where:** ti84-trainer-v2/app.js:750 + 765 (physicalMode default true), app.js:2485-2506 (physicalAdvance: no error/hint tracking), app.js:3050-3052 ('Press ${keyLabel}' always shown), app.js:2070-2088 (recallQuality(0,0)=5), app.js:2125-2129 (guided lastQuality=4 fixed), app.js:2177-2193 (score: quality/5 to gradebook)

**Suggested fix:** Tag recorded attempts with mode ('physical' vs 'emulator') and either cap physical-mode score (e.g. 0.6 'practiced') or record it as participation-only; require the answer-verification step (typing the computed result) to earn full credit in physical mode — that's the only observable evidence the procedure was actually run. Also reconsider the default: boot into emulator mode when no preference is saved.

### 7. [high] (content) Wizard choice fields (Inpt Data/Stats, alternative hypothesis, invNorm Tail, Pooled) are scripted without the ENTER commit

On the real TI-84 family OS, a choice row's highlighted option is only committed by pressing ENTER — arrowing onto an option and then pressing DOWN leaves the previous selection active (TI's own guides say 'highlight Stats and press [enter]'). The step data scripts these rows as cursor moves only: t-test-stats step 5 is a single RIGHT with narration 'Switch Inpt from Data to Stats' (ti84-procedures-data.json:5637, repeated at :6021 and :6343 for the 2-samp variants), the alternative row is 'RIGHT ... until the desired relation is highlighted' followed directly by DOWN, and invNorm's Tail row is RIGHT [repeatable] then DOWN (:3549, :4863). This pattern recurs across roughly 10 wizard procedures (t-test stats/data, 2-samp t test/int Pooled row, 1/2-prop z tests, invnorm, invnorm-sampling). If the real OS requires ENTER, the trainer is rehearsing a keystroke habit that on a physical exam-day calculator silently runs the test with the default alternative (≠) or default Data mode — wrong p-value, no error shown. It would also make the ROM-backed mode visibly diverge: the WebCEmu firmware screen would still show 'Data' fields while the trainer narrates 'Enter the sample mean' (the walkthrough validates the student's keypress against step.key at app.js:2387; the emulator just renders). The native simulation suite passes because it implements the same selection-follows-cursor assumption — it cannot catch this class of divergence from real firmware.

**Where:** ti84-procedures-data.json:5637,6021,6343,3549,4863; ti84-trainer-v2/app.js:2387

**Suggested fix:** Verify on the real WebCEmu ROM (load T-Test, press RIGHT then DOWN, observe whether Stats fields appear). If ENTER is required as classic OS behavior indicates, insert an ENTER confirmation step after every choice-field selection across the affected procedures, update the native form-engine to match, and re-run the verification suite. This is exactly the kind of step the trainer exists to drill — forgetting ENTER on the alternative is a top real-world student error.

## Lens-level impressions

### student-ux

This is an ambitious, genuinely impressive piece of courseware: a real TI-84 Plus CE ROM running in WASM, a parallel native state machine that validates every keypress, a two-track SM-2 scheduler (pattern recognition + procedure execution), branch walkthroughs that turn wrong answers into contrast lessons, and a clutch system that cleanly separates guided steps from free exploration. The data layer (29 authored procedures with per-step commonErrors coaching, confusion-matrix contrasts) is the kind of content most commercial tools don't have. The day-old gradebook wiring is also done carefully (signed-out users skip cleanly).

But viewed as a student walks through it, the learning loop leaks at exactly the points the architecture exists to protect: recall mode displays the answer (narration, mock-screen footer, and wrong-key messages all name the next key), the default physical mode is an honor-system that records perfect scores to the teacher's gradebook, and Track 1 can be brute-forced by cancelling branches. On phones the situation is worse: the banner — the only feedback channel — is hidden, and the default physical mode has no escape hatch to Options or the emulator. Add a jargon-only first-run screen ('Track 2 validates each key with the native state machine') and a brand-new 16-year-old has no idea what this tool wants from them. Finally, 2-PropZTest/ZInt — core AP Unit 6 procedures — are fully authored but silently filtered out (the same defect the known native test failure points at).

The good news: most of the high-severity items are copy/gating fixes (gate narration by mode, add a mode toggle to the physical panel, route the banner into the mobile narration bar, author two pattern-data entries), not architecture work. Fixing the recall leak + physical-mode scoring before the Sept 2026 cohort would make the recorded 'trainer' data trustworthy and the SRS actually do its job; a per-procedure progress view is the biggest motivational lever after that.

### content

Content quality is unusually rigorous for a side tool — menus and wizard fields were verified against a real ROM dump (STAT TESTS 18-item ordering, DISTR menu, wizard field tables all match CE OS 5.8.2), the native suite walks every procedure data-driven (83/84 pass; the lone failure is a stale count pin), and unit tagging is 100% complete: all 29 procedures carry numeric units 1-9, and the new ledger write (app.js:2184) guards with Number.isFinite before stamping 'U'+n, so the f18c2ea recording path is sound for every procedure a student can reach. The two real problems: (1) the two newest procedures (2-PropZTest/2-PropZInt, core U6 content) are silently filtered out of the trainer because they never got pattern-recognition backfill — app.js:206 gates the entire procedure list on signature presence; and (2) a systemic keystroke pattern omits the ENTER commit on wizard choice fields (Inpt, alternative hypothesis, Tail), which against real TI-84 OS behavior would teach students a habit that silently runs the wrong test on exam day — this needs one session of verification against the bundled WebCEmu ROM. Coverage maps well to inference-heavy units (U6-U9) but U3 has zero procedures (no randInt/seed) and U4 lacks the discrete-RV mean/SD FreqList skill — both inside or adjacent to the SUMMER26 U1-U5 prep window, making them the highest-value content additions before September. The pattern track (27 signatures, 22 confusion pairs, 62 canonical problems) is genuinely good at stem-to-procedure recognition but has no output-interpretation drills, the other half of the exam skill.

### stability

Overall this is a well-engineered app for its class: every layer of the ROM pipeline has a designed user-visible fallback (no hangs — failures land in 'simplified mode' with a status pill and banner), the build is deterministic (node build.mjs exits 0 and reproduces the committed generated/* and standalone.html byte-for-byte), Desk iframe open/close is clean (src='about:blank' discards the document; re-open is a fresh init from the IDB ROM cache — no leaks, no double-init, no focus stealing, no audio), and the new roster wiring is correctly fire-and-forget with double-fire protection (app.walkthrough is nulled before a second finish-review click can land) and a working unit guard (procedure.unit is an int in all 29 data entries, so Number.isFinite passes). Suite results: root `npx vitest run tests/ti84-state-machine.test.js tests/ti84-plot.test.js` = 107/107 passed (54+53, 2 files); native suite = 359 passed / 1 failed of 360 (the known stale pin at verify-all-procedures.test.js:241 expecting 27 procedures vs 29 in data). The real risks cluster in three places: (1) the ROM cache lifecycle — an IndexedDB failure wrongly aborts a download that doesn't need IDB, and a corrupt-but-version-current cached ROM is never auto-invalidated, both of which strand students in simplified mode; (2) unguarded localStorage.setItem in the save paths, which in quota/private-mode browsers throws after state mutation but before render(), stranding the UI and silently never persisting SM-2 progress; and (3) a subtle predicate mismatch in the new roster guard (current() vs token()) that can resurrect exactly the red 404-link nudge the guard was written to suppress. All are small (S-effort) fixes. The permanently-red native test pin should be fixed before the Sept 2026 cohort work ramps up, so red actually means something again.

### architecture

A genuinely well-shaped small app with better-than-average discipline for this repo: the build is deterministic (verified byte-identical on rebuild), standalone.html is currently in perfect sync with sources, math/menus/forms live in nine small dual-export native/ modules with 359 passing tests, and app.js delegates math to stat-math rather than duplicating it. The shape of the risk is process, not code quality: (1) the one artifact students actually load (standalone.html, via the Desk's absolute GH Pages URL) is produced by a manual `node build.mjs` with no npm script, no drift test, and one historical commit proving the stale-prod failure mode already happened; (2) yesterday's content addition (two-prop procedures) shipped without native support and left the native suite permanently red via a hard-coded 27-procedure pin while its real assertions are soft — the worst combination, a failing test everyone ignores guarding nothing; (3) the highest-stakes logic (SM-2 scheduling that drives every student's review queue, the answer-tolerance matcher that judges student answers, and the day-old gradebook write) is locked inside a 3,687-line zero-export IIFE with no tests. The fixes compound: export a buildStandalone() + drift test (S), extract three pure seams using the native/ pattern already in the repo (the build inliner needs no new machinery), then pin SM-2/tolerance/record-payload behavior. The eager multi-MB ROM download in a default mode that never shows the emulator is the one student-facing perf win available for the Sept cohort.

### integration

Yesterday's wiring (f18c2ea) is structurally sound: recordTrainerAttempt -> gradebookClient.record() -> POST /ledger/record matches the frozen ledger contract exactly (itemId 'TI84-<kebab-id>' fits the [A-Za-z0-9-] charset, unit 'U<n>' matches the DN2b convention, score quality/5, upsert on attempt:1), nothing in the chain can throw into the practice loop, and the rows are correctly grade-inert (parseItemLesson and computeGrade both ignore them by design, per migration 0016's stated intent). The weakness is not the shape but the silence: there is no confirmation anywhere — no UI indicator, no client test, no teacher aggregate — that a single trainer row has ever landed, and migration 0016 is USER-RUN with no recorded evidence it was executed (the sibling 0017 demonstrably hit not-provisioned live on deploy day). The two data-design choices worth revisiting before a cohort accumulates data are the attempt:1 upsert overwriting better scores with worse ones (against the repo's raise-only convention) and the recorded_at column never refreshing on upsert (which quietly breaks the teacher's only recency view for ALL sources, not just the trainer). The path to counting is clear and cheap — a unit-scoped trainer track needs only a procedures-per-unit manifest server-side plus a max-score policy client-side — and teacher visibility is a ~20-line additive field on /class/grades since the ledger rows are already fetched there and discarded. No exam-date or seasonal assumptions exist in the trainer; it ages cleanly into the Sept 2026 cohort.
