### Helper function signatures and semantics

All four functions go into a new file `.v6-frq-decomp-block.js`, wrapped in the same IIFE pattern as `.v5-ladder-block.js` (`(function(window){ ... })(typeof window !== 'undefined' ? window : globalThis);`), publishing `window.__studyGuideV6__`.

**`getFrqDecomposition(questionId)`**
- Signature: `(questionId: string) => DecompEntry | null`
- Reads `window.FRQ_DECOMPOSITIONS` (the parsed JSON, set by a `<script src="data/frq-decompositions.json">` tag or by the HTML via a fetch at init — see Batch C for loading mechanism).
- Returns `null` if `window.FRQ_DECOMPOSITIONS` is falsy or `questionId` not found.

**`recordHelperUsed(unit, kind, payload, state)`**
- Signature: `(unit: number, kind: 'formula'|'mcq-correct'|'mcq-wrong', payload: string, state: object) => void`
- `payload` is the formulaId (for kind `'formula'`) or questionId (for MCQ kinds).
- Mutates `state.units[unit].frqHelpers`. Must initialize `frqHelpers` if absent.
- Dedup rule: `'formula'` — if payload already in `frqHelpers.formulasViewed`, no-op. `'mcq-correct'` or `'mcq-wrong'` — if payload already in `frqHelpers.mcqDrills` (as any value), no-op (first-use wins).

**`computeEffectivePenalty(frqHelpers, decomposition)`**
- Signature: `(frqHelpers: object, decomposition: DecompEntry | null) => number`
- Returns `0` if `frqHelpers` is null/undefined or `decomposition` is null.
- Formula penalty: each unique formulaId in `frqHelpers.formulasViewed` that appears in any skill's `supportingFormulas[]` → +0.05. Cap contribution at one count per unique ID even if it appears in multiple skills.
- MCQ penalty: each key in `frqHelpers.mcqDrills` → if value is `'correct'` → +0.10; if `'wrong'` → +0.15.
- Cap result at `decomposition.maxPenalty` (0.50).

function handleHelperClick(kind, id, unit, data, questionId) {
  if (!data.frqHelpers) data.frqHelpers = defaultFrqHelpers();

    // Show confirmation modal
    showFrqHelperModal(() => {
      data.frqHelpers.confirmed = true;

function doHelperAction(kind, id, unit, data, questionId) {

## 7. Risks and Pitfalls

**1. Block-scope oddity at line 294.** The bare `{` at line 294 encloses all v4 code and closes at line 783. The v5 IIFE (`(function(window){...})(...)`) lives at lines 784-1423 and is itself INSIDE the `<script>` IIFE but OUTSIDE the bare-{ block. The v6 paste must go at line 1424 or later — outside the bare-{ block. Batch C must read the structure carefully (the v5 IIFE end is at line 1423 exactly) and paste after that line. If Codex accidentally pastes inside the bare-{ block, JavaScript will throw a ReferenceError because `'use strict'` is active there.

**2. normalizeState v5→v6 migration: doseLadder and dailyDose gating.** Currently (line 1571-1576), `doseLadder` is copied only if `schemaVersion === 5`, and `dailyDose` the same. After Batch C, both conditions must be `=== 5 || === 6`. If Codex forgets to update this, v6 users will lose their dose ladder on every page reload. This is easy to miss because it is a non-obvious conditional far from the version bump.

**3. Penalty cap interaction with paper-mode pass-through.** `computeEffectiveScore('paper', penalty)` must return `effective: null` — not `1.0 * (1 - penalty)`. The `renderGrade` call site must check `effScore.effective !== null` before rendering the effective score div. If the check is missing, paper-mode FRQs will show a nonsensical effective score line.

**4. `activeProbe.questionId` not matching a known gate.** If a student navigates to a formula probe (MCQ), `questionId` will be something like `'U1-L10-Q02'` — `isFrqGate` will be false, and the existing remediation path runs. But if a student somehow arrives at an FRQ gate whose ID is not in `frq-decompositions.json` (e.g., a legacy ID that doesn't match exactly), `getFrqDecomposition` returns null and Batch C's code must fall through to the "Skill details are unavailable" graceful fallback. Codex must not accidentally render broken HTML in this case.

**5. `frqHelpers` persisting across probe changes.** Per the spec, `frqHelpers` is per-unit and survives probe changes. This means if a student views an FRQ, triggers the confirmation modal, and then navigates away to an MCQ and comes back to the same FRQ, `confirmed` is still `true` and they see no second modal. This is intentional per Fork 5, but Codex must not accidentally wire `advanceDailyQueue` to reset `frqHelpers`. Verify that the `advanceDailyQueue` / `setActiveProbe` code paths do not touch `data.frqHelpers`.
