# WALLET_LOADING_SPEC.md — load paper wallets into the roster without typing, and keep the keys

**Purpose:** today the only way to attach a student's Dogecoin address is a `prompt()` on the dashboard and typing a
34-character address by hand from a printed sheet. The teacher wants (1) a no-typing way to load the addresses the
node's paper-wallet generator produced, and (2) the private keys held too, so a lost paper wallet is a reprint, not a loss.

> **Status:** proposed (2026-09-05). **Owner:** teacher. **Workflow:** brainstorm → this spec → implement (orchestrator or
> Codex). **Policy change, stated plainly:** the payout-rail rule P8 ("no private key ever touches roster-server") is
> relaxed for TEACHER-CUSTODY wallets only. The teacher's words: "not strictly trustless, but I am the teacher — play
> pretend." Keys are stored encrypted (AES-256-GCM via the existing `roster-server/crypto.js`, the same mechanism the
> reversible student passwords use), readable only through a teacher-gated endpoint, never sent to any student surface.

## 1. Goals / Non-goals

Goals:
1. **Bulk load**: paste (or upload) the generator's KEYS CSV into the dashboard, assign wallets to students in one screen,
   submit once. Addresses land in `doge_address` through the existing validated path.
2. **Keys kept**: the WIF for each assigned wallet is stored encrypted; the teacher can reveal one (to re-print a lost
   paper wallet) or export the mapping for cold storage. A student never sees a key.
3. **Scan instead of type** for one-offs: a "📷 Scan QR" button on the address cell opens the laptop camera and reads the
   address QR (and optionally the WIF QR) straight off the paper sheet.
4. Nothing about payouts, candy, or the conservation identity changes.

Non-goals:
- No key generation in the browser; no key on any student surface; no decrypt endpoint callable with a student token.
- No change to the self-custody proposal path (still off).
- No rotation/re-encryption tooling in v1 (the env key is set once; document it).

## 2. Data model — migration `0035_wallet_custody.sql` (additive, idempotent, USER-RUN)

```sql
alter table doge_account
  add column if not exists doge_wif_enc   text,          -- AES-256-GCM ciphertext (crypto.js envelope), NULL = not held
  add column if not exists doge_wallet_label text,       -- "Wallet #17" from the generator, for the reprint
  add column if not exists doge_key_held_at timestamptz;
```
Until it runs, the new endpoints 503 (`isDogeMissing()` pattern). `doge_wif_enc` is never selected by any student-facing
query (`/wallet`, `/wallet/chain`, `/class/wallets` keep their explicit column lists — add a test that greps them).

Env: `WALLET_KEY_SECRET` (32+ bytes, Railway). Missing env → the store/reveal endpoints 503 with
"wallet custody key not configured"; address loading still works without it.

## 3. Endpoints (extend `mountDogeWallet`)

| Endpoint | Auth | Effect |
|---|---|---|
| `POST /wallet/address` (existing) | teacher | unchanged; the bulk loader calls it per student |
| `POST /wallet/custody` | teacher | body `{studentId, wif, label}`; validates the WIF (base58check, mainnet prefix — reuse the generator's decoder in a shared `tools/lib/doge-keys.mjs`), **derives the address from the WIF and refuses (409) if it differs from the student's `doge_address`**, encrypts, writes `doge_wif_enc/label/held_at`. Never logs the WIF. |
| `GET /wallet/custody/:studentId` | teacher + `?confirm=1` | returns `{wif, address, label}` decrypted — for the reprint. Audit row in `doge_ledger kind='key_reveal'`. |
| `DELETE /wallet/custody/:studentId` | teacher | clears the held key (student went self-custody, or key rotated). |
| `GET /class/wallet-custody` | teacher | `{studentId → {held: bool, label, heldAt}}` for the panel badges. No key material. |

## 4. Dashboard UX (Reward Disbursement panel)

**"📥 Load wallets" button** → modal:
1. A textarea "Paste the KEYS CSV" (or file input). Parsed client-side: `label,address,wif,privHex`; rows validated
   (address regex, WIF decodes to that address — done client-side with the same shared decoder, so a pasted typo is
   caught before any request).
2. An assignment table: one row per **student without an address** (active roster, sorted by section then name), each
   with a dropdown of **unassigned** wallets (default: next unused label in order — "Wallet #1 → first student", so the
   teacher can also just click "Assign in order"). Wallets already on the roster (address match) are greyed with the
   student's name.
3. Checkbox "Also keep the private keys (teacher custody)" — default ON. A one-line note: keys are stored encrypted on the
   server, visible only to you, so a lost sheet can be reprinted.
4. Submit → for each row: `POST /wallet/address`, then `POST /wallet/custody` (if checked). Progress list with per-row
   ✓/✗; failures stay in the table for retry. Nothing is written until Submit.

**Per-student**: the address cell gains **📷 Scan** (jsQR from cdnjs, `getUserMedia` on the laptop camera; reads the
address QR; a second "scan WIF" step if custody is on) and **🔑 held** / **🔑 reveal** (shows the WIF + a "Reprint sheet"
hint: `node tools/doge-wallet-gen.mjs --reprint --wif <…> --label "<label>"`). Reveal requires a typed `REVEAL` confirm
(mirrors the backup card's `RESTORE`). Nothing in the student Desk changes.

## 5. Generator addition — `--reprint`

`tools/doge-wallet-gen.mjs --reprint --wif <WIF> --label "Wallet #17" [--out sheet.html]`: re-derives the address, renders
the same one-wallet HTML sheet (address QR + WIF QR + warnings). Offline, Node built-ins only, like the rest of the tool.
Refuses if the derived address is not mainnet.

## 6. Invariants (each maps to a test)

- K1: no student-token route ever returns `doge_wif_enc` or a decrypted key (grep the column lists + a request-level test).
- K2: `POST /wallet/custody` refuses a WIF whose derived address ≠ the student's stored address (409), so a key can never
  be attached to the wrong wallet.
- K3: the WIF never appears in server logs or error payloads (the endpoint echoes only `label` and the last 4 of the address).
- K4: bulk load is idempotent — re-submitting the same CSV assigns nothing new and changes no existing address.
- K5: reveal writes an audit ledger row and requires the confirm flag; without `WALLET_KEY_SECRET` it 503s, never leaks.
- K6: the payout rail's seal/complete path is byte-identical (conservation suites stay green).
- K7: client-side WIF→address derivation matches the generator's for the test vectors in `tests/doge-wallet-gen.test.js`.

## 8. Open decisions (defaults chosen)

- Keep keys by default when bulk-loading **[default: yes — the whole point]**.
- Where the encryption key lives **[default: Railway env `WALLET_KEY_SECRET`, like the password key; a copy in the
  teacher's password manager]**.
- Scan the WIF QR too, or only the address **[default: both, second step optional]**.
- Export the whole mapping (labels, addresses, WIFs) as a downloadable CSV **[default: no in v1 — the generator's KEYS CSV
  on the laptop is already the cold copy; revisit if the teacher wants an app-side export]**.

### TL;DR
Paste the generator's KEYS CSV into a dashboard modal, assign wallets to students in one click, submit once: addresses
go through the existing validated write, private keys are stored AES-encrypted under a teacher-only reveal for reprints.
A camera QR scan covers one-offs. No typing, no student ever sees a key, payouts untouched.
